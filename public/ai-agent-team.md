# はじめに

「個人ではAIエージェントをバリバリ使えているのに、チームに導入しようとすると急に難しくなる」

これは私が開発チームをリードしていたときに実感したことです。私のチームは **自分+未経験メンバー2人+少し経験のあるメンバー3人** の6人構成で、ChatGPTとClaude Codeを開発に取り入れていました。

AIを「自分の生産性を上げる道具」として使うのと、「チームの生産性を上げる仕組み」として導入するのは、まったく別の問題です。この記事では、小規模チームでAIコーディングエージェントを導入するときの手順を、実際にやってみて学んだことベースでまとめます。

**対象読者**

- チームにAIエージェントを導入したいリーダー・テックリード
- 未経験・ジュニアメンバーを抱えるチームの先輩エンジニア
- 「個人では使えるけど、チームでのルールがない」状態の人

# 個人利用とチーム導入は別物、という話

個人でAIを使うとき、出力が間違っていても困るのは自分だけです。自分で気づいて、自分で直せば済みます。

チームに入れた瞬間、話が変わります。

- **AIの出力は、すべてが正しいわけではない**。しかし未経験メンバーには「どこが間違っているか」を見抜く力がまだない
- 間違いを含んだコードがそのままPRに乗り、レビューをすり抜けると、チーム全体の負債になる
- 「AIが書いたから」という理由で、誰もそのコードを説明できない状態が生まれる

つまりチーム導入とは、ツールのインストールではなく、**「AIの間違いをチームとして検出する仕組みづくり」** です。これを前提に、以下の手順で進めます。

# STEP1: ツールを選ぶ

2026年現在、主要なAIコーディングエージェントはおおよそ次のような棲み分けになっています。

| ツール | 形態 | 特徴 | チーム導入の観点 |
| --- | --- | --- | --- |
| Claude Code | CLI(+IDE拡張/デスクトップ) | 長時間の自律実行、大規模な変更・リファクタに強い | 委任型。レビュー可能な単位でタスクを切る運用が必要 |
| GitHub Copilot | IDE拡張+GitHub統合 | 補完が高速、Issue→PR→ReviewがGitHub上で完結 | 導入ハードルと単価が低く、全員配布しやすい |
| Cursor | AI統合IDE(VS Codeフォーク) | 書きながらの編集・差分レビューの体験が良い | VS Codeからの移行が容易。エディタごと変える決断が要る |
| Codex CLI | CLI | サンドボックス内実行、オープンソース | コードレベルでカスタマイズ可能 |
| Gemini CLI / Cline など | CLI / VS Code拡張 | 無料枠・BYOKで試しやすい | コストを抑えてまず試す選択肢 |

※料金プランは変動が激しいので、導入時に必ず公式を確認してください。

私のチームでは **ChatGPT(調査・壁打ち用)と Claude Code(実装用)** の組み合わせでした。

> **ポイント:** 「全員に同じツール」より「用途でツールを分ける」方がうまくいきました。調査・学習はChatGPT、コードを書くのはClaude Code、と役割を分けることで、「なんでもAIに丸投げ」になりにくくなります。

# STEP2: ツールより先に「ルール」を決める

導入してから一番効いたのは、ツールの設定ではなくこのルールでした。

## ルール:「AIが書いたコードも、自分で理解して説明できること」

私のチームで決めていた一番大事なルールです。

- PRを出す人は、AIが生成したコードであっても **1行ずつ「なぜこう書いたか」を説明できる** 状態にしてから出す
- レビューで「ここはどういう意図?」と聞かれて「AIがそう書いたので」は禁止
- 説明できない部分が残っているなら、それは「まだ理解が追いついていないコード」なのでPRに入れない

このルールには2つの効果があります。

1. **品質の防波堤になる**: AIの間違いに最初に気づけるのは、コードを「理解しようとした」本人です
2. **未経験メンバーの教育になる**: 「説明できるまで調べる」過程が、そのまま学習になります。AIに書かせて終わり、では人が育ちません

## そのほか決めておくとよいルール

- **AI生成コードの扱いをコミット・PRで明示するか**(例: PRテンプレートに「AI使用箇所」欄を作る)
- **機密情報・顧客コードをプロンプトに貼らない**(契約・セキュリティ要件の確認)
- **AIの提案を採用しない自由**を明文化する(「AIがこう言ってるから」で議論を終わらせない)

# STEP3: コードレビュー運用に組み込む

AI導入後、レビューの役割が変わります。**「コードの間違い探し」から「理解の確認」へ** です。

私のチームで効果があったやり方:

- レビューで「このコードを自分の言葉で説明して」と口頭・コメントで確認する。説明が詰まる場所は、だいたいAIの出力を鵜呑みにしている場所
- AIの出力は **定期的に確認する前提** で運用する。一度動いたコードでも、「本当にこの書き方でいいのか」を、週次の振り返りなど決まったタイミングで見直す

> **実感として:** AIが出したものはすべて正しいわけではなく、定期的な確認が必要です。「導入したら終わり」ではなく、「確認のサイクルをどう回すか」が運用の本体でした。

# STEP4: 未経験メンバーに使わせるときの注意点

未経験2人と一緒に運用して学んだ、やってはいけないこと:

1. **いきなり実装をAIに丸投げさせない** — まず「AIなしで書ける小さなタスク」で基礎をつくる。基礎がないと、AIの間違いに気づけない
2. **「動いたからOK」で終わらせない** — 動くコードと正しいコードは別物。説明責任ルール(STEP2)とセットで運用する
3. **エラー文をそのままAIに貼って、答えをそのまま貼り返す癖を放置しない** — 「エラー文のどこを読んだ?」を先に聞く
4. **AIの回答を教材として鵜呑みにさせない** — AIは古い書き方や存在しないAPIを自信満々に出すことがある。公式ドキュメントで裏取りする習慣をセットで教える

# 導入チェックリスト(保存用)

チームにAIエージェントを導入するとき、これだけ確認すれば大枠は外しません。

- [ ] 用途ごとのツールを決めた(調査用/実装用)
- [ ] 料金プランとライセンス(商用利用・チームプラン)を確認した
- [ ] 機密情報の取り扱いルールを決めた
- [ ] **「AIが書いたコードも自分で説明できること」をルール化した**
- [ ] PRテンプレート/レビュー観点を更新した
- [ ] AI出力を定期的に見直すサイクル(週次など)を決めた
- [ ] 未経験メンバー向けに「AIなしで書く」練習フェーズを用意した
- [ ] 「AIの提案を採用しない自由」をチームで共有した

# まとめ

- チーム導入の本質はツール選定ではなく、**AIの間違いをチームとして検出する仕組みづくり**
- 一番効くルールは **「AIが書いたコードも、自分で理解して説明できること」**
- AIの出力はすべて正しいわけではない。**定期的な確認のサイクル**まで含めて「導入」
- 未経験メンバーには、AIを「答えをくれる人」ではなく「裏取りが必要な同僚」として扱わせる

小さいチームほど、ルールはシンプルな方が機能します。まずは「説明できること」の1つから始めるのがおすすめです。
