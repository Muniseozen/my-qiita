# はじめに

Qiitaに毎日投稿する、と決めました。理由はシンプルで、学んだことを言語化する習慣を作りたかったからです。

ただ、毎日投稿には明確な敵が2ついます。

1. **ネタ切れ** — 3日目くらいから「今日何書こう…」が始まる
2. **執筆時間** — 1本に2時間かかると、平日は無理

そこで、普段の開発で使っているClaude Codeを「編集者」として組み込んだ執筆体制を作りました。この記事では、その体制の全体像と、**「AIに書かせた記事の量産」にしないために決めたルール**を紹介します。

:::note warn
先に書いておくと、この記事は「AIで記事を自動生成しよう」という話ではありません。むしろその逆で、AIと書くからこそ必要になったルールの話が後半のメインです。
:::

# 体制の全体像

毎日のフローはこうなっています。

```
ネタ帳(ストック) → トレンド調査 → 構成の壁打ち → ドラフト共同執筆
→ 実体験・判断で穴埋め(ここは人間) → GitHubでバージョン管理 → 投稿
```

1本あたりの所要時間は、小ネタ記事で30分〜1時間程度です。それぞれ説明します。

## 1. ネタ帳をClaudeと共有しておく

まず最初にやったのは、記事ネタを思いつきで考えるのをやめて、**ネタ帳を作ってClaudeと共有する**ことでした。

ネタ帳には次のものを入れています。

- 投稿方針(毎日=小ネタ、週1=大型記事、の2層構成)
- 大型記事の候補リスト(タイトル案+概要+タグ案まで書いておく)
- 小ネタの「型」(エラー解決ログ、コマンド1つ深掘り、シリーズ物など)

ポイントは、**「ネタ」ではなく「型」をストックする**ことです。「今日はこの型で、今日の開発で起きたことを書く」と決まっていれば、ネタ探しの時間がゼロになります。

## 2. トレンド調査はClaudeに任せる

書く前に「今Qiitaで何が読まれているか」をClaudeにWeb検索で調べてもらいます。

実際、この体制を作る前に調べてもらったところ、「自分が書こうとしていた定番ネタ」と「今トレンドで読まれているもの」が結構ズレていることが分かりました。ここは自分の思い込みより、その日のデータを見る方が確実です。

## 3. ドラフトは共同執筆。ただし「核」は人間が出す

ここが体制の中心です。やり方は、Claudeにゼロから書かせるのではなく、**先にインタビューさせる**形にしています。

実際の流れ:

1. 記事テーマを決めたら、Claudeから「実体験について質問」が来る(チーム規模は?実際に困ったことは?決めていたルールは?など)
2. 自分は箇条書きや口頭レベルの雑な文章で答える
3. Claudeがそれを核にして構成・文章を組み立てる
4. 自分しか書けない部分は `【ここに実体験】` のプレースホルダーで残してもらう
5. プレースホルダーを自分で埋めて完成

この順番にすると、記事の核(経験・判断・失敗談)は必ず自分のものになり、AIが担当するのは構成・言い回し・調査の部分になります。

タイトル・タグ・Description(OGP用の概要文)もドラフトの先頭にコメントで入れてもらうと、投稿時のコピペだけで済みます。

## 4. 記事はGitHubで管理する

書き上がった記事はMarkdownファイルとしてGitHubで管理しています。このやり方は以前記事にしたので、詳細は「【2026年最新版】Qiitaの記事をGitHubで管理して自動投稿する【手順まとめ】」をどうぞ。

https://qiita.com/Munise/items/542c3504397a48ab7246

毎日投稿との相性が良くて、

- 記事の修正履歴が残る
- 「書きかけ」をブランチやドラフトとして置いておける
- Claude Codeから直接ファイルを読み書きできる

という利点があります。

# 「AIに書かせた記事」にしないためのルール

ここが一番書きたかった部分です。

前職でAIをチーム開発に導入したとき、**「AIが書いたコードも、自分で理解して説明できること」というルール**を決めていました。AIの出力はすべてが正しいわけではなく、定期的な確認が必要だと痛感したからです。

記事執筆でも同じルールを適用しています。

## ルール1: 自分で説明できない記事は出さない

ドラフトに自分の知らない用語・コマンド・数値が入っていたら、調べて理解するか、削除します。コメントで質問されたときに「AIがそう書いたので」としか答えられない記事は、出す意味がないからです。

## ルール2: 記事の核は必ず実体験にする

構成や言い回しはAIに任せても、「何が起きたか」「どう判断したか」「何に失敗したか」は自分の言葉で出します。逆に言うと、**実体験が1つもないテーマは書かない**。これはネタ選びのフィルターとしても機能します。

## ルール3: 技術情報はAIの出力を鵜呑みにしない

バージョン、料金、仕様などはAIが古い情報や間違った情報を出すことがあるので、公式ドキュメントで裏取りします。コードは必ず手元で動かしてから載せます。

# やってみて分かったこと

- **一番時間が溶けていたのは執筆ではなく「ネタ決め」だった。** 型のストックとトレンド調査の自動化で、着手までの時間がほぼゼロになった
- **インタビュー形式は、記事のためだけでなく自分の振り返りになる。** 「あのとき何でああしたんだっけ」を言語化させられるのは、思った以上に学びがある
- **AIと書くと、むしろ「自分にしか書けない部分」がはっきりする。** 構成や一般論はAIで埋まるからこそ、経験談の価値が相対的に上がる

# まとめ

| 工程 | 担当 |
| --- | --- |
| ネタ帳・型のストック | 人間+Claude |
| トレンド調査 | Claude(Web検索) |
| 構成・ドラフト | Claude |
| 実体験・判断・失敗談 | **人間(ここは渡さない)** |
| 技術情報の裏取り・動作確認 | 人間 |
| バージョン管理 | GitHub |

毎日投稿はまだ始めたばかりなので、この体制がどこまで持つかは未知数です。1ヶ月続いたら、運用してみての改善点をまた記事にしようと思います。

同じようにAIと記事を書いている方の工夫があれば、ぜひコメントで教えてください。
