# はじめに

私は少し変わった経歴で、エンジニアになる前は**テレビ制作会社のAD(アシスタントディレクター)**を2年やっていました。

エンジニアに転身したとき、正直こう思っていました。

**「AD時代の経験なんて、何の役にも立たない。完全にゼロからのスタートだ」**

実際、技術の面ではそのとおりでした。コードは書けない、用語はわからない、年下のエンジニアの方がはるかに詳しい。AD時代の2年間は、キャリアとしては回り道だったと本気で思っていました。

ところがその後、未経験メンバー2人を含む6人の開発チームをリードすることになって、気づいたんです。**テレビ現場で叩き込まれた時間の文化が、そのまま使える**場面がたくさんあることに。

この記事は、「役に立たない」と思っていたテレビ業界の「巻き」の文化を、開発チームに持ち込んだ話です。

# 「巻き」とは何か

テレビ現場には、時間に関する独特の言葉があります。

| 用語 | 意味 |
| --- | --- |
| **押し(押してる)** | 予定より遅れている状態 |
| **巻き(巻いてる)** | 予定より早く進んでいる状態。「巻きで!」=急いで、前倒しで |
| **香盤表** | 撮影の段取りを分単位で書いた進行表。誰が・いつ・どこで・何をするかが全部載っている |

そしてテレビ現場には、絶対に動かない前提が1つあります。

**放送時間は、1秒も動かない。**

システム開発の締切は(本当は良くないですが)交渉すれば動くことがあります。放送は違います。19時の番組は19時に始まる。だから現場の全員が、**「締切を動かす」という選択肢が存在しない世界**で時間を管理しています。

この環境で2年働くと、時間に対する感覚が体に染みつきます。そしてこの感覚、開発チームの運営とめちゃくちゃ相性が良かったんです。

# 持ち込んだ文化1:締切は動かさない。動かすのは「中身」

テレビでは、収録が押したら放送を遅らせる……なんてことはできません。やるのは**中身の調整**です。コーナーを1本削る、トークを短くする、それでも時間内に収める。

開発チームでも同じ発想で運営しました。

- スプリントの期限が危うくなったら、**期限ではなくスコープを調整する**(この機能は次のスプリントへ、など)
- 「ちょっと延ばしましょう」を基本的に選択肢にしない

アジャイルでいう「タイムボックス」の考え方そのものなのですが、私はアジャイルの教科書より先にテレビ現場でこれを覚えていました。期限がズルズル延びるチームは、締切を「調整可能なもの」として扱っているところから始まっている気がします。

# 持ち込んだ文化2:「押してる」は秒で共有する

テレビ現場では、進行が押した瞬間に全員に伝わります。「押してます」の共有が遅れるほど、後の工程の調整が効かなくなるからです。逆に言うと、**早く共有さえすれば、巻き返す手段はいくらでもある**。

開発チームでは、これを毎日の**夕会**で仕組み化しました。その日の進捗と明日やることを毎日15分で共有する場です。

- 遅れ(押し)が**24時間以上隠れない**構造になる
- 「押してます」を言うことは悪ではなく、**言うのが遅いことが悪**という文化を作れる
- 早く分かれば、タスクの分担変更や巻き取りなど、打ち手がまだある

テレビで学んだのは「押し自体は日常。問題は押しの報告が遅れること」という感覚です。これは開発でもまったく同じでした。

# 持ち込んだ文化3:香盤表の発想でタスクを割る

香盤表は、撮影日の動きが**分単位**で書かれた進行表です。「なんとなく今日はロケ」ではなく、「9:00 機材搬入、9:30 リハ、10:15 本番1カット目…」と全部割ってある。だから誰かが見れば「今、予定通りか」が一目で分かります。

開発チームでは、タスクを**1〜2日で終わる粒度**まで分解して管理していました(プロジェクト情報をAIに学習させて分解のたたき台を作らせると、ここは一瞬です)。

粒度が香盤表レベルに細かいと:

- 「進んでいるか」が毎日見える(ふわっとした2週間タスクは、押していても2週間気づけない)
- 「どこで押したか」が特定できるので、次の見積もりが上手くなる

段取りを制する者が現場を制す——ADが最初に叩き込まれることですが、スプリントも結局は段取りです。

# 持ち込んだ文化4:カンペの文化=ぶっつけ本番にしない

スタジオ撮影には**カンペ**があります。台本と合わせて、**誰が・いつ・何を言うか**まで事前に決まっていて、本番はそれを実行する場です。即興に見えるトークの裏でも、進行の骨組みは全部準備されている。つまりテレビの本番とは、**「考える場」ではなく「準備したものを実行する場」**なんです。

開発チームでも、この分離をそのまま使いました。

- **リリースや本番環境での作業は、手順書を書いてから実行する。** ぶっつけでコマンドを打たない。本番は考える場ではない
- 未経験メンバーに渡すタスクも、つまずきそうな箇所は手順化しておく。カンペがあるから本番(実作業)で固まらない
- デモやレビューで「見せる」ときも、流れを決めてから臨む

私は今でも「未経験の人がつまずかない手順書」を書くのが好きなのですが、振り返るとこれは完全にカンペ文化の出身だからだと思います。**本番で人を迷わせないために、先回りして紙(ドキュメント)を用意しておく**——ADの仕事そのものです。

# 持ち込まなかったもの:「気合で巻く」文化

一方で、テレビ現場の全部を持ち込んだわけではありません。

テレビの「巻き」には、**人間の体力と根性で時間を圧縮する**側面があります。寝ないで編集する、気合で終わらせる。あの世界はそれで回っていましたが、開発チームに持ち込むと確実に壊れます。

- 開発で「気合で巻く」=雑なコードと技術的負債。**ソフトウェアの品質は根性では巻けない**
- 徹夜で書いたコードの尻拭いは、翌週の自分とチームがやることになる

なので、「巻き」の**時間感覚**だけを持ち込んで、「巻き」の**根性文化**は置いてきました。ここの取捨選択は大事だと思います。

# まとめ:AD用語→開発チーム変換表

| テレビ現場 | 開発チームでの対応物 |
| --- | --- |
| 放送時間は動かない | タイムボックス(期限でなくスコープを調整) |
| 「押してます」は秒で共有 | 夕会での毎日の進捗・詰まり共有 |
| 香盤表 | 1〜2日粒度のタスク分解 |
| カンペ・台本 | 手順書(本番作業・リリースはぶっつけでやらない) |
| 段取り八分 | 前日に「明日やること」まで決めて帰る |
| 気合で巻く | **持ち込まない**(品質は根性で巻けない) |

# おわりに:「前職の経験なんて役に立たない」と思っているあなたへ

転身したばかりの頃の私は、本気でそう思っていました。技術はゼロ。経歴書に書けるスキルもない。AD時代の2年は、ただの回り道だったと。

技術がゼロだったのは事実です。そこはごまかせませんし、地道に勉強するしかありませんでした。

でも、チームを任されたときに私を助けてくれたのは、勉強した技術ではなく、**テレビ現場で毎日浴びていた文化**の方でした。締切への感覚、押しをすぐ共有する癖、段取りとカンペの習慣——技術は後からでも学べましたが、この文化は2年間毎日浴びたからこそ染みついたものです。

もしあなたが異業種からエンジニアになって、「前職の経験なんて役に立たない」と感じているなら:**役に立たないのは前職の「業務知識」であって、前職で染みついた「文化」はたぶんこれから武器になります。** それが何かに気づくのは、少し後——チームで働き始めたときかもしれません。

異業種出身のエンジニアの方、あなたの前職から持ち込んで機能した文化があれば、ぜひコメントで教えてください。
